# 主張単位の根拠監査（スキル候補 S1）

- 状態: 草案（skills-drafts）。適用実績なし。
- 作成日: 2026-11-02

## 0. 根拠区分の標準名称（決定）

本スキルでは、根拠区分を次の3つの標準名称で記す。関連文書の別名は下表のとおり対応付ける。

| 標準名称 | 定義 | 既存文書での呼び名（出典） |
| --- | --- | --- |
| 確認済み | 監査者が今回、根拠（一次情報・実測・連携先データ等）を参照し、主張内容と一致することを確かめた | 「確認済み」muse-setup-v2.md:211 / v3.md:214 / v4.md:214。「確認できた事実」muse-setup-v1.md:22。【実測】app-build-guide_v4.md:11 / v5.md:11。【確認済】app-build-guide_v4.md:239 / v5.md:240。「根拠（確認したこと）」apps/uranai/AUDIT_v5.md:8。「実測」apps/shusshin/README.md:24 |
| 評価・解釈 | 判断・推論・推定・予測・推奨・比較・一般化。根拠となる事実があっても、主張自体が判断であればこの区分 | 「推定」muse-setup-v2.md:213 / v3.md:216 / v4.md:216。「評価」muse-setup-v1.md:22。【評価】app-build-guide_v4.md:239 / v5.md:240。「調査＋推定」「推定」apps/shusshin/README.md:24 |
| 未確認 | 根拠がない、根拠を取得していない、取得に失敗した、または根拠と主張が一致しない | 「未確認」muse-setup-v1.md:22 / v2.md:214 / v3.md:217 / v4.md:217、apps/uranai/AUDIT_v5.md:8、apps/uranai/README.md:23。【未確認】app-build-guide_v5.md:670。【着想】（公式資料未検索の部分）app-build-guide_v5.md:11 |

### 0.1 決定の根拠

- 3区分の構成と「評価・解釈」の名称: 本スキルの依頼文の指定による。
- 「確認済み」「未確認」の表記: muse-setup-v2〜v4 §6.2 の表記（送り仮名「み」あり）を採用。app-build-guide の【確認済】は同義の別名として扱う。
- 「未確認」は確認した全文書で同じ語が使われており、表記揺れはない。

### 0.2 3区分に直接対応しない既存区分の扱い

| 既存区分（出典） | 本スキルでの扱い |
| --- | --- |
| 本人申告（muse-setup-v2.md:212 / v3.md:215 / v4.md:215） | 「本人が〜と述べた」という主張は、発言記録を根拠に確認済み。発言の中身は、別途検証しない限り未確認 |
| 【ユーザー既定】（app-build-guide_v4.md:11 / v5.md:11） | 「ユーザーが〜を方針として明示した」という主張は、指示の記録を根拠に確認済み。方針の妥当性は監査対象外 |
| 【着想】（app-build-guide_v4.md:11 / v5.md:11） | 製品の一般知識に基づく記述は、一次情報で照合するまで未確認。その記述から導いた設計判断は評価・解釈 |
| 【未確定】（app-build-guide_v5.md:524 ほか） | 要件の未回答を示す区分で、根拠区分ではない。本スキルの対象外 |
| ○／△／×（app-build-guide_v5.md §13） | 採否の判定で、根拠区分ではない。対象外。ただし同 §13.1 の4（v5.md:404）「未確認は ○ にしない」と矛盾する記述は指摘する |

- 0.2 の対応付けは本スキル作成時の評価・解釈であり、各文書の作成者による確定ではない。
- 既存文書の表記は変更していない。文書間の表記揺れは残っている。

## 1. 適用する場面

- 監査レポート・README・調査報告・エージェントの回答を、公開・採用・引き継ぎ前に検査する。
- 文書内の「確認済み」「実測」等の自己申告ラベルが正しいかを検査する。

適用しない場面:

- 要件の欠落検出（app-build-guide_v5 §14 を使う）。
- 機能・素材の採否判定（app-build-guide_v5 §13 を使う）。

## 2. 入力と出力

- 入力: 監査対象の文書（ファイルパスと版、またはコミット）。参照可能な根拠（ファイル、URL、コマンド出力、データ）。
- 出力: 主張台帳（§4.1）、集計（§4.2）、指摘一覧（§4.3）。

## 3. 手順

### A1 対象の固定

1. 対象のファイルパス、版またはコミット ID、監査日を記録する。
2. 監査中に対象が変わった場合は、A1 からやり直す。

### A2 主張の分割

1. 対象を、真偽または妥当性を個別に判定できる最小単位（主張）に分ける。
2. 主張ごとに C1, C2… の ID を付け、原文の位置（ファイル:行）と原文を改変せず記録する。
3. 1文に事実と判断が混在する場合は分ける。例:「通過率は 100% で、品質は十分」→ C1「通過率は 100%」、C2「品質は十分」。
4. 表・箇条書き・脚注・注記・図の説明も対象に含める。抜き取りはしない。
5. 数値・日付・固有名詞・数量を含む部分は、それぞれ独立した主張として扱う。

### A3 根拠の対応付け

1. 各主張に、根拠の所在を記録する: ファイル:行、URL、コマンドと出力、データの位置。
2. 根拠の種類を記録する: 一次情報／二次情報／実測／発言・指示の記録。
3. 取得日時を記録する。価格・規約・仕様など変わりやすい情報は必須。
4. 監査者が今回、実際に参照した根拠だけを記録する。記憶・推測による根拠は記録しない。
5. 文書内に出典の記載があっても、監査者が参照していなければ「根拠あり」としない。

### A4 照合

主張ごとに、根拠と照合した結果を次のいずれかで記録する。

| 照合結果 | 条件 |
| --- | --- |
| 一致 | 根拠を参照し、主張と内容が一致した |
| 不一致 | 根拠を参照し、主張と内容が矛盾した |
| 根拠なし | 根拠が示されていない、または見つからない |
| 取得失敗 | 根拠の取得を試みたが失敗した（失敗の内容を記録） |

- 取得失敗と「該当なし」を区別する（muse-setup-v4.md §6.2 と同じ扱い）。

### A5 区分の判定

1. 主張が判断・推論・推定・予測・推奨・比較・一般化であれば、評価・解釈とする。その判断が依拠する主張の ID を記録する（依拠先が未確認なら指摘に挙げる）。
2. それ以外の主張は、照合結果で決める。
   - 一致 → 確認済み
   - 根拠なし／取得失敗 → 未確認
   - 不一致 → 未確認とし、指摘一覧に「誤り」として必ず挙げる
3. 判定に迷う場合は、確認の度合いが低い区分に倒す（確認済み → 未確認、事実 → 評価・解釈）。
4. 二次情報だけで一致した主張は確認済みとし、根拠の種類欄に「二次情報」と残す。

### A6 ラベルの照合

1. 対象文書が主張に付けている区分ラベル（確認済み、実測、推定、未確認等）を記録する。
2. 0章の対応表で標準名称に読み替え、A5 の判定と比べる。
3. 食い違いはすべて指摘一覧に挙げる。特に、文書が「確認済み」「実測」とし、A5 で未確認となったものは重大とする。

### A7 報告

1. §4 の様式で、主張台帳・集計・指摘一覧を出す。
2. 監査で参照できなかった根拠、分割しきれなかった箇所は、未確認として列挙する。
3. 修正案は書かない。修正するかどうかは対象文書の作成者が判断する。

## 4. 出力様式

### 4.1 主張台帳

| ID | 位置 | 原文 | 根拠（所在・種類・取得日時） | 照合結果 | 区分 | 文書側ラベル | 依拠先 ID |
| --- | --- | --- | --- | --- | --- | --- | --- |

記入例（架空）:

| ID | 位置 | 原文 | 根拠（所在・種類・取得日時） | 照合結果 | 区分 | 文書側ラベル | 依拠先 ID |
| --- | --- | --- | --- | --- | --- | --- | --- |
| C1 | README.md:10 | テストは 14 項目すべて通過 | `node tests/run.js` の出力・実測・2026-11-02 10:00 | 一致 | 確認済み | 検証済み | — |
| C2 | README.md:10 | 実機でも問題ない | なし | 根拠なし | 評価・解釈 | （なし） | C1 |
| C3 | README.md:12 | 上限は 16 MB | 公式文書 URL・一次情報・取得失敗（403） | 取得失敗 | 未確認 | 確認済み | — |

### 4.2 集計

- 主張数（総数）、区分別件数（確認済み／評価・解釈／未確認）、照合結果別件数（一致／不一致／根拠なし／取得失敗）。
- 集計は台帳の全件から出す。抜き取り集計はしない。

### 4.3 指摘一覧

| 重大度 | ID | 指摘 | 種別 |
| --- | --- | --- | --- |

- 種別: 誤り（不一致）／ラベル過大（文書側が確認済み・実測、監査は未確認）／ラベル過小／依拠先未確認（評価・解釈の依拠先が未確認）／根拠なし／取得失敗。
- 重大度: 重大（誤り、ラベル過大）／要対応（依拠先未確認、根拠なし、取得失敗）／軽微（ラベル過小、表記揺れ）。

## 5. 禁止事項

- 主張の抜き取り・サンプル監査。
- 監査者が参照していない根拠による「確認済み」判定。
- 対象文書の書き換え。修正案の提示（依頼された場合を除く）。
- 取得失敗を「該当なし」「問題なし」と記録すること。
- 文書側のラベルを、照合せずにそのまま採用すること。

## 6. 完了条件

- 対象の全主張に ID・照合結果・区分がある。
- 確認済みの主張すべてに、所在と取得日時を持つ根拠がある。
- 評価・解釈の主張すべてに、依拠先 ID または「依拠先なし」の記録がある。
- 集計の合計が台帳の件数と一致する。
- 指摘一覧に、不一致・ラベル過大がすべて含まれる。

## 7. 限界（未確認）

- 主張の分割粒度は監査者の判断を含み、監査者によって件数が変わり得る。分割基準の再現性は未検証。
- 作成者自身による監査は独立監査ではない（apps/uranai/AUDIT_v5.md:5、apps/shusshin/AUDIT_v5.md:3 と同じ制約）。
- 本スキルは未適用で、所要時間・精度は未測定。
