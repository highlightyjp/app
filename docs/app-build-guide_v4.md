# アプリ作成 統一指示書（v4）

Oct 20, 2026 · @highlightyjp

## 0. 使い方・適用範囲・優先順位

新規アプリ作成の最初に参照する基礎規約です。個人アプリの実作業（V1〜V19の改版）で確定した事項と、パッケージ製品の設計要素、OWASP Top 10:2025 を統合しています。

- 適用範囲: Claudeのアーティファクト（単一HTML）で作るブラウザ完結型アプリ。業務ツールにも流用できます。
- 優先順位: ① その場のユーザー指示 → ② 本書 → ③ 一般的な慣習。指示と本書が衝突したら指示に従い、衝突した事実を報告します。
- 根拠の区分: 【実測】この環境で確認済み ／ 【ユーザー既定】ユーザー本人が明示した方針 ／ 【着想】製品の一般知識（公式資料は今回未検索のため未確認）。区分のない記述は規約です。
- 版: v4（2026-10-21）。v3 からの変更: §14（業務要件→要件定義 変換ロジック）を追加。14.10 に実行環境差の確認を追加。v3（2026-10-21）。v2（2026-10-21）からの変更: 一次情報による確認結果を §11.5・§12 に反映、§13 に法律家（P8）・判定基準・同一基準の原則を追加して再判定、§9 のチェックリストに §13 の項目を追加。v1（2026-10-20）からの変更: §3・§10 のデジタル庁デザインシステムを一次情報で更新、§10〜§13 を追記。§0〜§9 の規約内容は変更していない（版表記・§3 の注記・§9 の項目追加・依頼テンプレートの版表記を除く）。改訂はこの文書に追記し、版を上げます。

## 1. 実行環境の前提と制約

この環境で実際に確認した事実と、それが設計に与える制約です。

| 事実 | 区分 | 規約 |
| --- | --- | --- |
| ページは単一HTMLで公開。CSPにより外部への直接fetchは不可。外部連携はランタイム機能（db・mcp・sample・user・downloads）経由 | 実測 | 直接の外部通信を前提にしない。必要な機能を着手時に列挙する |
| 機能宣言（capabilities）は全量宣言。再公開のたびに全部を書かないと外れる | 実測 | 公開コマンドに常に全量を付ける。最小のツールだけを宣言する |
| ランタイムの版（contract）は固定。今回は 0.2.66（最新 0.2.87） | 実測 | 版の引き上げはユーザーが意図したときだけ |
| DBは1文書＝1関心事。既存文書の書込は版番号（if\_version）必須。batchは最大50件・原子的。個人領域は data/users/me | 実測 | 競合を前提に設計。個人データは個人領域だけに置く |
| コネクタ（mcp）はツール単位で宣言。初回は利用許可を求められる。失敗コード（未接続・再認証・未許可等）は継続不可として停止する | 実測 | 許可・未接続の案内文を用意する。継続可能な失敗とは分ける |
| Claudeへの問い合わせ（sample）は遅く、利用枠を消費する。ページ内ルール計算は約1秒 | 実測 | 標準はページ内計算。AIは任意の選択とし、オフが初期値 |
| 公開範囲はアプリ側で変更できない。公開結果に「リンクを知っている全員」「本人のみ」が表示される（実際に両方を観測） | 実測 | 公開のたびに共有表示を確認し、ユーザーに伝える |
| ページは16MB以内。外部スクリプトは許可されたCDNと完全なバージョン指定のみ | 実測（ツール仕様） | 外部ライブラリは原則使わない |
| 検証に使えるのはサーバ側の疑似ブラウザ（jsdom）。実ブラウザのCSP・描画を再現しない | 実測 | 画像・外部通信・見た目は「実機で未確認」と報告する |
| 手元の端末はiPhoneのみ（PCなし）。手順の案内はiPhoneで完結する形 | ユーザー既定 | 操作はすべて画面内で完結。PC前提の手順を書かない |
| ブラウザ完結・サーバー不要・単一ファイルを好む | ユーザー既定 | 独自サーバーを立てない |
| SVGを出すときは必ずPNGに変換して納品。文字入りPNGはNoto Sans CJK JP | ユーザー既定 | 画像納品時に適用 |
| APIプロキシは model・max\_tokens・messages だけを受け付ける | ユーザー既定（過去の構築での制約） | APIプロキシ経由の構築で適用 |

## 2. 設計の基本原則

【ユーザー既定】の作業方針を、アプリ作成での具体的な規則に落としたものです。

1. 仕様凍結: 既存の仕様・定数・構造・スキーマ・入出力形式を無断で変えない。変更はユーザーが明示したときだけ。善意の「改善」「最適化」「一般化」も無断では行わない。
2. フェーズ管理: 完了・凍結済みのフェーズに手を加えない。未着手のフェーズを先行実装しない。指定されたフェーズだけを対象にする。
3. 逸脱・不整合の報告: 問題は指摘するが、無断で書き換えない。逸脱・不整合を見つけたら必ず報告する。
4. 全量・網羅: データを恣意的に削減・簡略化しない。「サンプルで足りる」と独自に判断しない。データ不足は欠陥として報告する。
5. 現実データ準拠: 現実のデータを優先する。取得できないものは推測で埋めず「取得できなかったもの」として表示する。
6. 事実と評価の分離: 事実の報告と、評価・予測・推奨を区別する。ツールで取得していない情報は「未確認」と明示する。
7. 判断を代行しない: 実行・検証・リスク指摘を行い、決めることはユーザーに残す。確認を求めるのは、曖昧なときと不可逆な操作のときだけ。
8. ユーザーデータの不可逆操作: 削除・上書きは、事前にエクスポート（バックアップ）を取り、版番号で固定して行う。明示指示のない削除はしない。
9. 縮退動作: 外部取得の失敗で全体を止めない。失敗した項目だけ既存値を保持し、件数を固定フォーマットで残す（エラー繰越）。
10. Claude非依存: 標準動作はページ内で完結させ、利用枠を使うAIは明示的な選択にする。更新・計算・提案を、Claudeの起動なしで行えるようにする。

## 3. パッケージシステムからの取り込み

Salesforce・Oracle・ServiceNow・汎用パッケージの設計思想のうち、単一HTMLファイル＋Artifact DBで実装できるものだけを採る。各製品の仕様は公式ドキュメント未検索のため【着想】（一般知識・未確認）。製品機能の再現は目的にしない。

| 出典 | 着想した考え方 | 本環境での実装規約 | 本アプリでの実績 |
| --- | --- | --- | --- |
| Salesforce | 重複ルール・保存ビュー・入力規則・項目の型 | 重複キー(dupKey)で重複検出。保存ビューを ui 文書に保持。入力はnormalizerで型・範囲を強制 | 重複検出、保存ビュー、NORM |
| Salesforce | データ品質の可視化（必須項目欠落） | 必須欠落を運用チェックに列挙 | 運用チェック「必須欠落」 |
| Oracle | 楽観的ロック・トランザクション・マイグレーション手順 | 既存文書の更新は if\_version 必須。複数文書は batch（原子的・50件以内）。移行は §4 の5手順 | if\_version更新、pinned batch移行 |
| Oracle | 監査証跡 | 変更履歴を audit 文書に保持（上限100件） | audit v1 |
| ServiceNow | 要対応キュー・ステート管理・変更管理 | 「要対応」を一覧化し、状態を固定語彙で持つ。変更前バックアップとロールバック手段を必須にする | 運用チェック、バックアップ/復元 |
| ServiceNow | CMDB的な構成管理 | 文書・スキーマ版・外部連携を構成カードで一覧表示 | 構成カード |
| 汎用パッケージ | データ鮮度・価格変動検知・在庫確認 | 外部由来の値に取得時刻を持たせ、鮮度超過・変動・欠品を検知 | 価格変動/在庫なし検知 |
| 汎用パッケージ | 設定駆動・権限分離・エラー可視化 | 閾値・重み・辞書は定数/設定に集約。書込系ツールを非宣言。エラーを {scope,ref,msg} で表示 | ENG定数、mcp最小宣言 |
| デジタル庁DADS | デザイントークン・アクセシビリティ | 色・余白をCSS変数化、ライト/ダーク2系統、状態は色＋文言 | トークン、badge |

注意・リスク

- 取り込みは「考え方」のみ。製品固有の用語・画面・挙動を再現済みとは書かない。
- 上表の出典の説明は一般知識で、公式未検索（未確認）。必要時は着手前に一次情報で確認する。ただしデジタル庁デザインシステムは 2026-10-21 に一次情報で確認済み（§12）。

## 4. データ設計規約

1. 全文書にスキーマ版 `v` を持たせる。版を上げる変更はユーザーの明示指示があるときだけ。
2. 入力の正規化を単一箇所（NORM）に集約し、保存・起動・スナップショット・復元の全経路で同一関数を通す。
3. 時刻は `YYYY-MM-DDTHH:mm+09:00`（JST・オフセット付き）。
4. id はホワイトリスト文字のみ。外部入力をそのまま id ・キーに使わない。
5. エラーは `{scope, ref, msg}` の構造で保持し、文字列だけで捨てない。
6. 読込に失敗した文書は、空データで上書きしない（readFail で保存を拒否）。
7. 監査文書は100件上限で古い順に落とす。
8. localStorage はユーザー単位の便宜（フィルタ・下書き）に限り、読み書きをすべて try/catch で囲む。正本を置かない。
9. バックアップのエクスポート/復元も NORM を通し、不正な型を取り込まない。

### スキーマ・文書構成の移行（5手順）

1. 旧データをエクスポートしてファイルに保存する（バックアップ）。
2. 新構造のデータを別ファイルとして生成する（旧データを直接編集しない）。
3. pinned（if\_version 指定）の batch で一括書込する。
4. 書込後に読み戻し、件数・主要項目を元データと突合する。
5. 旧文書の削除はユーザーが明示したときだけ。明示がない間は旧文書を残し、残存を報告する。

リスク

- batch は50件超で分割が必要。分割した場合、全体としては原子的ではない。途中失敗時はバックアップから復元する。

## 5. 画面・操作規約

1. デザイントークンは CSS 変数（`:root`）。ダークモードを `@media (prefers-color-scheme: dark)`（`:root:not([data-theme="light"])`）と `:root[data-theme="dark"]` の2系統で定義し、`body` に明示的な背景を持たせる。
2. iPhone 幅で完結する。左右16pxの余白、横スクロールなし、タップ領域44px以上。PC前提の操作（右クリック・ホバー必須）を使わない。
3. 状態表示は ok/warn/err/info の badge＋文言。色だけに意味を持たせない。
4. エラー文言は「何が・原因・次の行動」の3点。
5. 空・読込中・部分失敗の3状態をすべて表示する。
6. 確認ダイアログは不可逆操作（削除・復元上書き）のみ。
7. CSV は BOM 付き UTF-8。ファイル出力は downloads 機能を使う。
8. 標準動作（計算・提案・検索）はページ内で完結させる。AI は明示オプション（設定スイッチ）。
9. 操作対象（選択中の文書・表示状態）は、画面内で現在地が分かる形で表示する。

未確認

- 44px という値は一般的なタップ領域の目安で、本環境でこの値を実機検証していない。
- iPhone 実機の見え方は jsdom では再現できない。実機確認はユーザーに依頼する。

## 6. セキュリティ規約

基準: OWASP Top 10:2025（top10.owasp.org/2025 で項目名を取得済み）。LLM連携は OWASP LLM Top 10 2025（genai.owasp.org/llm-top-10 で取得済み）。以下の「本環境対策」は本環境の制約に合わせた実装規約であり、OWASPの記述そのものではない。

### 6.1 OWASP Top 10:2025 対応表

| 項目 | 本環境対策（規約） |
| --- | --- |
| A01 Broken Access Control | 公開範囲を公開結果で確認し、「リンクを知っている人」が読める状態を報告。共有設定は Claude が変更しない。DB・mcp は閲覧者権限で動くことを前提に設計。 |
| A02 Security Misconfiguration | capabilities を最小宣言（不要なものを宣言しない）。公開ごとに全量を再宣言し、差分を確認。contract を固定している場合は、新版との差を報告。 |
| A03 Software Supply Chain Failures | 外部 script は cdnjs / jsdelivr / unpkg 等の許可元のみ、版を完全固定。単一HTMLで完結する場合は外部依存ゼロを優先。 |
| A04 Cryptographic Failures | 機密（ID番号・カード・口座・パスワード）を DB・localStorage・バックアップに保存しない。バックアップファイルは平文。保管場所はユーザー責任として報告。 |
| A05 Injection | `innerHTML` への外部・ユーザー入力の直挿入を禁止。必須のエスケープ関数を通す。外部取得 HTML は DOMParser でホワイトリストのサニタイズ。`eval`/`new Function` はデータに適用しない。 |
| A06 Insecure Design | 不可逆操作にバックアップを必須化。外部取得失敗時は既存値保持（§2-9）。読込失敗時は上書き拒否（§4-6）。 |
| A07 Authentication Failures | 独自認証を実装しない（パスワード・トークンをページで扱わない）。認証はプラットフォーム側（claude.ai アカウント）に任せる。 |
| A08 Software or Data Integrity Failures | 読込・復元データを NORM で検証。バックアップは版 `v` と件数を確認。更新は if\_version で競合検出。 |
| A09 Security Logging and Alerting Failures | 変更とエラーを audit 文書に記録。重要エラーを運用チェックで表示。機密をログに残さない。 |
| A10 Mishandling of Exceptional Conditions | すべての非同期・外部呼出を try/catch。失敗を握り潰さず、{scope,ref,msg} で表示。部分失敗を明示。 |

※ A01、A04、A07 はプラットフォーム側で決まる部分が大きく、ページ側で完結できない。プラットフォームの内部挙動は未確認。

### 6.2 本環境固有の追加対策

1. 公開範囲: 公開結果の共有表示を毎回確認して報告する。個人データを扱うページは、共有をユーザーが変更するとデータ読取範囲が変わる可能性を明記する（mcp 共有時の権限は未確認）。
2. mcp は最小ツールのみ宣言（読取系のみ）。書込・送信・削除系ツールをページから呼べるようにしない。
3. 外部取得したコンテンツは信頼しない（データ扱い）。リンクは http/https のみ許可し、`javascript:` 等を除去。
4. LLM 連携（OWASP LLM Top 10 2025 のプロンプトインジェクション・出力の不適切な取扱・過度な権限付与に関連）: 入力はすべてデータ扱い。DB 内容も入力扱い。出力はスキーマ＋ref ホワイトリストで検証。LLM に書込権限を与えない。AI は明示選択時のみ。
5. ユーザー識別子（メールアドレス等）を無関係な外部サービスに送らない。
6. 過去版・バックアップに秘密を埋めない（公開履歴の保持仕様は未確認）。
7. テストハーネス（jsdom）は CSP を再現しない。CSP 由来の不具合は「実機未確認」として報告する。
8. iPhone 紛失・端末共有を想定し、画面に表示する個人情報（住所・予定・購入履歴）を最小化する。
9. 外部取得（TinyFish 等）のコスト・回数制限を無視しない。一括取得は件数上限を設ける（制限値は未確認）。

リスク

- 上記をすべて設定しても、ページ内のコード・データは閲覧者から見える。秘密を埋め込んではならない。
- A03 の具体的な許可元リストはプラットフォーム仕様で、変更されうる。公開時の拒否メッセージを優先する。

## 7. 品質・検証・報告

### 検証手順

1. タスクリストの最後を「検証」にする。
2. 変更前にページ・DBをバックアップする（ページは版ごとにファイル保存）。
3. 構文チェック: `new Function` で script をパース。
4. jsdom で全タブを巡回し、変更機能を個別に実行。外部呼出はモック。
5. DB 変更は読み戻して突合。
6. 公開結果（共有表示を含む）を確認。
7. チェックできなかった項目は「未確認」として報告。

### 報告形式（監査指摘形式・最小）

- 結論
- 修正点
- 未確認・不可
- 問題点・リスク（肯定のみの報告をしない）
- Sources（ツールで実際に取得した情報源のみ）

### 判定基準

- jsdom で通り、実機を確認していない機能は「実機未確認」とする。
- 定量的な主張（速度・件数）は計測値と計測環境（jsdom）を併記する。
- ユーザーの訂正を受けたときは、反映範囲を列挙して報告する。

## 8. 公開・変更管理・運用

1. 既存のページは同一ファイルパスで更新する。別パスは別アプリを作るときだけ。
2. 公開ラベルに「V番号＋要約」を付け、変更内容を追えるようにする。
3. 公開ごとに capabilities を全量で再宣言する（省略と空オブジェクトの挙動差に注意）。
4. 変更を分類する: (a) ページのみ変更／(b) データ変更／(c) スキーマ変更。(b)(c) は §4 の移行手順とバックアップを必須とする。
5. ロールバック用に前版のページファイルを残す。
6. 公開結果の共有表示が変わった場合、変更した設定はユーザーに報告する（Claude は共有を変更できない）。
7. ユーザーが編集した可能性のあるページは、更新前に現在の公開版を読み、競合を確認する。
8. 継続セッションでコンテキストが圧縮された場合は、ページファイルの最新コピー（スクラッチパッド）を正本として扱う。

リスク

- スクラッチパッドはセッション単位で、セッション終了後の保持は未確認。公開済みページからの read をバックアップ手段とする。

## 14. 業務要件→要件定義 変換ロジック（RT）

【着想】本書独自。EARS（要件記法）を文型に借用。検証結果は 14.9。業務部門が曖昧・自由記載で書いた要望を、システム要件文・受入基準・§9 依頼テンプレートへ機械的に変換する。

### 14.1 使い方（業務部門向け・3手順）

- 手順1: 困りごと・やりたいことを、そのまま書く。曖昧でよい。IT用語は不要。例「月末の請求書チェックが大変。間違いがないようにしたい」
- 手順2: AI が質問を出す。選択肢で答える。1回5問まで。「分からない」も有効な回答。
- 手順3: AI が「読み戻し文」を出す。違う箇所だけ直す。OK と答えた内容が依頼書（§9）になる。
- AI は目的・範囲・数値・承認者などを決めない。聞く（14.3）。

### 14.2 変換規則 RT-1〜RT-9

- RT-1 原子化: 入力を句点・読点で 1文＝1要求に分け、S1, S2… の ID を付ける。原文は改変せず保持する。前後6字未満の断片は隣と結合する。
- RT-2 スロット検出: 各要求について 誰が／何を／いつ・きっかけ／どうする／どれくらい／例外 の有無を見る。欠落は推測で埋めず、質問にする。
- RT-3 曖昧語照合: 14.4 の辞書で照合する。1語でも該当すれば、その要求は「要確認」。該当語ごとに対応する質問を必ず出す。
- RT-4 タイプ分類: 14.5 の10タイプのいずれかを付ける（複数可）。該当なしは「分類不能」とし、Q-PURPOSE を出す。
- RT-5 機能候補の写像: 14.6 の語一致で F1〜F7 等を「候補」として付す。候補は採用ではない。採否は §13 の基準で判定し、決定はユーザー（13.7）。
- RT-6 質問規則: 14.7 の固定順で出す。1ラウンド5問まで。選択式を原則とする。同じ質問を繰り返さない。必須質問（G-NEWEXIST, G-DATA, G-ENV, G-ENVCHK, G-USERS, G-DONE, G-PURPOSE の7問は依頼ごとに1回、G-PRIORITY は要件ごとに1回）は必ず出す。
- RT-7 要件文化: 回答が揃った要求だけを 14.8 の文型で要件文にする。未回答の項目は【未確定】と明記して残す。推測で埋めない。
- RT-8 確定条件: 「確定候補」は、曖昧語なし かつ スロット欠落なし かつ タイプ分類可、の全てを満たす要求だけ。それ以外は「要確認」。「確定」はユーザーの読み戻し承認でのみ成立する。
- RT-9 出力: 要件一覧（ID・原文・タイプ・要件文・受入基準・機能候補・状態）と、§9 依頼テンプレートの自動記入結果、§13 判定（機能候補ごと）を出す。最後に平易な読み戻し文を出す。

### 14.3 AI が決めてよいこと／ユーザーに聞くこと

- AI が決めてよい: 表現の整形、ID 付番、タイプ分類、辞書照合、機能候補の提示、14.10 の安全側既定値の適用（適用したと明記する）。
- ユーザーに聞く: 目的、対象データ、個人情報・機密の有無、「など・その他」の中身、数値（件数・日数・期限・閾値）、判断者・承認者、閲覧範囲、優先度、完了条件、使う環境。
- ユーザーの回答と矛盾する既定値は適用しない。

### 14.4 曖昧語辞書（A〜H。検証版 84語）

- A 程度・主観 → Q-NOW, Q-VOL, Q-FREQ: すぐ／早く／なるべく／できるだけ／簡単／分かりやすい／わかりやすい／見やすい／いい感じ／ちゃんと／ちゃんとした／しっかり／適切／適宜／必要に応じて／大変／面倒／楽に／スムーズ／使いやすい
- B 量 → Q-VOL: たくさん／多い／少ない／少なく／少し／大量／いくつか／大体／多数
- C 範囲 → Q-LIST: など／その他／全部／すべて／全て／いろいろ／色々／各種／一式／諸々
- D 時 → Q-FREQ, Q-DEADLINE, Q-WHEN: 定期的／随時／都度／月末／期限まで／そのうち／最近／早め／遅れ／たまに／毎回／近い／滞
- E 人 → Q-WHO, Q-DECIDE: 担当者／関係者／上長／上司／みんな／誰でも／先方
- F 結果の保証 → Q-ERR, Q-CHECK: 間違／ミス／漏れ／抜け／忘れ／二重／ダブり／滞らない／チェック
- G 指示語・省略 → Q-REF: それ／あれ／例の／いつもの／前と同じ／同様／同じ形式／前と同
- H 例外・条件 → Q-EX: 基本的／原則／ただし／場合によ／例外／特別／除く／以外

### 14.5 要件タイプ

- BF 業務フロー（申請・承認・差戻し・進捗・状態）／DT データ（台帳・マスタ・項目・履歴）／UI 画面・入力・検索／CL 計算・判定・照合／NT 通知・期限／AC 権限・閲覧／IF 取込・出力・連携／NF 非機能（件数・端末・保存期間）／CN 制約・規程（個人情報・社外持出し）／OP 運用（保守・引継ぎ）

- F1 入力規則: 間違／ミス／必須／形式／桁／範囲／入力
- F2 変更履歴と復元: 履歴／誰がいつ／変更／元に戻／記録を残／監査
- F3 状態遷移と承認: 申請／承認／差戻／却下／ステータス／状態／進捗／確認済／完了／滞

### 14.7 質問バンク（固定順。22問）

- Q-PURPOSE 誰の、どんな作業を、どうなったら助かりますか？（例付き自由記載）［必須］
- Q-WHO この作業をするのは誰（役割）で、何人くらいですか？（1人／2〜5人／6〜20人／21人以上）
- Q-NOW 今はどうやっていますか？（Excel／紙／メール／既存システム／その他）
- Q-ERR どんな間違い・困りごとが起きていますか？（入力ミス／転記ミス／抜け・漏れ／二重／期限超過／その他）
- Q-CHECK 「チェック・確認」は何と何を突き合わせることですか？（照合元と照合先）
- Q-WHEN いつ、何がきっかけで始まりますか？（毎日／毎週／毎月（何日）／発生したとき／その他）
- Q-FREQ どのくらいの頻度ですか？（毎日／週1／月1／不定期）
- Q-VOL 1回に扱う件数は？（〜10件／〜100件／〜1,000件／それ以上）
- Q-DEADLINE 期限は？何日以内、何日前に気づきたいですか？（当日／3日／7日／その他）
- Q-DECIDE 誰が判断・承認しますか？（役割で）
- Q-LIST 「など・その他・全部」に含まれるものを全て挙げてください。
- Q-REF 「それ・前と同じ・いつもの」は具体的に何ですか？（見本添付可）
- Q-EX 例外はどんな場合で、どう扱いますか？
- Q-NOTIFY 気づけないと困ることは？誰にいつ知らせますか？（画面内表示で足りるかも確認）
- Q-WHAT-DATA 扱う情報に個人情報・機密は含まれますか？（含まない／個人情報／機密／両方）［必須］
- Q-VIEW 誰にどの情報まで見せてよいですか？（全員／部署内／本人と上長のみ／その他）
- Q-OUT 結果はどう使いますか？（画面で見る／CSV で出す／印刷／他システムへ渡す）
- Q-KEEP 記録をどれくらい残しますか？（1か月／1年／3年／ずっと／分からない）
- Q-ENV どこで使いますか？（PC／スマホ／社内のみ／社外からも）［必須］
- Q-END 何ができたら「終わり」ですか？
- Q-DONE できたか、どう確かめますか？（確かめ方の例を1つ）［必須］
- Q-PRIORITY それぞれ「絶対必要／あれば良い／今回はいらない」のどれですか？［必須］
- 欠落スロットとの対応: 誰が→Q-WHO、何を・どうする→Q-PURPOSE、いつ・きっかけ→Q-WHEN、どれくらい→Q-VOL。

### 14.8 要件文の文型（EARS 5パターン＋複合）

- 常時: 「システムは、<応答>しなければならない。」
- 事象: 「<きっかけ>のとき、システムは、<応答>しなければならない。」
- 状態: 「<状態>の間、システムは、<応答>しなければならない。」
- 望ましくない状況: 「<望ましくない状況>の場合、システムは、<応答>しなければならない。」
- 任意機能: 「<機能>を備える場合、システムは、<応答>しなければならない。」
- 複合: 上記を組み合わせる。
- 受入基準は「<操作>すると<結果>になる」の1文で書く。数値は回答値のみを使う。回答がない数値は【未確定】とする。
- 例（回答済みの場合のみ）: 「経理担当が請求書を登録するとき、システムは、金額が数字以外なら登録を拒否し、理由を表示しなければならない。」← F1 候補。
