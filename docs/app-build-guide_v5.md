# アプリ作成 統一指示書（v5）

Oct 20, 2026 · @highlightyjp

## 0. 使い方・適用範囲・優先順位

新規アプリ作成の最初に参照する基礎規約です。個人アプリの実作業（V1〜V19の改版）で確定した事項と、パッケージ製品の設計要素、OWASP Top 10:2025 を統合しています。

- 適用範囲: Claudeのアーティファクト（単一HTML）で作るブラウザ完結型アプリ。業務ツールにも流用できます。
- 優先順位: ① その場のユーザー指示 → ② 本書 → ③ 一般的な慣習。指示と本書が衝突したら指示に従い、衝突した事実を報告します。
- 根拠の区分: 【実測】この環境で確認済み ／ 【ユーザー既定】ユーザー本人が明示した方針 ／ 【着想】製品の一般知識（公式資料は今回未検索のため未確認）。区分のない記述は規約です。
- 版: v5（2026-10-22）。v4 からの変更: §15（共有データの排他制御・時刻・参照通信）を追加。§1 の外部通信の行に §15.9 への参照を追記。§9 のチェックリストに §15 の項目を追加し、依頼テンプレートの版表記を v5 にした。v4（2026-10-21）。v3 からの変更: §14（業務要件→要件定義 変換ロジック）を追加。14.10 に実行環境差の確認を追加。v3（2026-10-21）。v2（2026-10-21）からの変更: 一次情報による確認結果を §11.5・§12 に反映、§13 に法律家（P8）・判定基準・同一基準の原則を追加して再判定、§9 のチェックリストに §13 の項目を追加。v1（2026-10-20）からの変更: §3・§10 のデジタル庁デザインシステムを一次情報で更新、§10〜§13 を追記。§0〜§9 の規約内容は変更していない（版表記・§1 の外部通信の行・§3 の注記・§9 の項目追加・依頼テンプレートの版表記を除く）。改訂はこの文書に追記し、版を上げます。

## 1. 実行環境の前提と制約

この環境で実際に確認した事実と、それが設計に与える制約です。

| 事実 | 区分 | 規約 |
| --- | --- | --- |
| ページは単一HTMLで公開。CSPにより外部への直接fetchは不可。外部連携はランタイム機能（db・mcp・sample・user・downloads）経由 | 実測 | 直接の外部通信を前提にしない。必要な機能を着手時に列挙する。例外は §15.9（参照のみの通信。既定は通信なし） |
| 機能宣言（capabilities）は全量宣言。再公開のたびに全部を書かないと外れる | 実測 | 公開コマンドに常に全量を付ける。最小のツールだけを宣言する |
| ランタイムの版（contract）は固定。今回は 0.2.66（最新 0.2.87） | 実測 | 版の引き上げはユーザーが意図したときだけ |
| DBは1文書＝1関心事。既存文書の書込は版番号（if\_version）必須。batchは最大50件・原子的。個人領域は data/users/me | 実測 | 競合を前提に設計。個人データは個人領域だけに置く |
| コネクタ（mcp）はツール単位で宣言。初回は利用許可を求められる。失敗コード（未接続・再認証・未許可等）は継続不可として停止する | 実測 | 許可・未接続の案内文を用意する。継続可能な失敗とは分ける |
| Claudeへの問い合わせ（sample）は遅く、利用枠を消費する。ページ内ルール計算は約1秒 | 実測 | 標準はページ内計算。AIは任意の選択とし、オフが初期値 |
| 公開範囲はアプリ側で変更できない。公開結果に「リンクを知っている全員」「本人のみ」が表示される（実際に両方を観測） | 実測 | 公開のたびに共有表示を確認し、ユーザーに伝える |
| ページは16MB以内。外部スクリプトは許可されたCDNと完全なバージョン指定のみ | 実測（ツール仕様） | 外部ライブラリは原則使わない |
| 検証に使えるのはサーバ側の疑似ブラウザ（jsdom）。実ブラウザのCSP・描画を再現しない | 実測 | 画像・外部通信・見た目は「実機で未確認」と報告する |
| 手元の端末はiPhoneのみ（PCなし）。手順の案内はiPhoneで完結する形 | ユーザー既定 | 操作はすべて画面内で完結。PC前提の手順を書かない |
| ブラウザ完結・サーバー不要・単一ファイルを好む | ユーザー既定 | 独自サーバーを立てない |
| SVGを出すときは必ずPNGに変換して納品。文字入りPNGはNoto Sans CJK JP | ユーザー既定 | 画像納品時に適用 |
| APIプロキシは model・max\_tokens・messages だけを受け付ける | ユーザー既定（過去の構築での制約） | APIプロキシ経由の構築で適用 |

## 2. 設計の基本原則

【ユーザー既定】の作業方針を、アプリ作成での具体的な規則に落としたものです。

1. 仕様凍結: 既存の仕様・定数・構造・スキーマ・入出力形式を無断で変えない。変更はユーザーが明示したときだけ。善意の「改善」「最適化」「一般化」も無断では行わない。
2. フェーズ管理: 完了・凍結済みのフェーズに手を加えない。未着手のフェーズを先行実装しない。指定されたフェーズだけを対象にする。
3. 逸脱・不整合の報告: 問題は指摘するが、無断で書き換えない。逸脱・不整合を見つけたら必ず報告する。
4. 全量・網羅: データを恣意的に削減・簡略化しない。「サンプルで足りる」と独自に判断しない。データ不足は欠陥として報告する。
5. 現実データ準拠: 現実のデータを優先する。取得できないものは推測で埋めず「取得できなかったもの」として表示する。
6. 事実と評価の分離: 事実の報告と、評価・予測・推奨を区別する。ツールで取得していない情報は「未確認」と明示する。
7. 判断を代行しない: 実行・検証・リスク指摘を行い、決めることはユーザーに残す。確認を求めるのは、曖昧なときと不可逆な操作のときだけ。
8. ユーザーデータの不可逆操作: 削除・上書きは、事前にエクスポート（バックアップ）を取り、版番号で固定して行う。明示指示のない削除はしない。
9. 縮退動作: 外部取得の失敗で全体を止めない。失敗した項目だけ既存値を保持し、件数を固定フォーマットで残す（エラー繰越）。
10. Claude非依存: 標準動作はページ内で完結させ、利用枠を使うAIは明示的な選択にする。更新・計算・提案を、Claudeの起動なしで行えるようにする。

## 3. パッケージシステムからの取り込み

Salesforce・Oracle・ServiceNow・汎用パッケージの設計思想のうち、単一HTMLファイル＋Artifact DBで実装できるものだけを採る。各製品の仕様は公式ドキュメント未検索のため【着想】（一般知識・未確認）。製品機能の再現は目的にしない。

| 出典 | 着想した考え方 | 本環境での実装規約 | 本アプリでの実績 |
| --- | --- | --- | --- |
| Salesforce | 重複ルール・保存ビュー・入力規則・項目の型 | 重複キー(dupKey)で重複検出。保存ビューを ui 文書に保持。入力はnormalizerで型・範囲を強制 | 重複検出、保存ビュー、NORM |
| Salesforce | データ品質の可視化（必須項目欠落） | 必須欠落を運用チェックに列挙 | 運用チェック「必須欠落」 |
| Oracle | 楽観的ロック・トランザクション・マイグレーション手順 | 既存文書の更新は if\_version 必須。複数文書は batch（原子的・50件以内）。移行は §4 の5手順 | if\_version更新、pinned batch移行 |
| Oracle | 監査証跡 | 変更履歴を audit 文書に保持（上限100件） | audit v1 |
| ServiceNow | 要対応キュー・ステート管理・変更管理 | 「要対応」を一覧化し、状態を固定語彙で持つ。変更前バックアップとロールバック手段を必須にする | 運用チェック、バックアップ/復元 |
| ServiceNow | CMDB的な構成管理 | 文書・スキーマ版・外部連携を構成カードで一覧表示 | 構成カード |
| 汎用パッケージ | データ鮮度・価格変動検知・在庫確認 | 外部由来の値に取得時刻を持たせ、鮮度超過・変動・欠品を検知 | 価格変動/在庫なし検知 |
| 汎用パッケージ | 設定駆動・権限分離・エラー可視化 | 閾値・重み・辞書は定数/設定に集約。書込系ツールを非宣言。エラーを {scope,ref,msg} で表示 | ENG定数、mcp最小宣言 |
| デジタル庁DADS | デザイントークン・アクセシビリティ | 色・余白をCSS変数化、ライト/ダーク2系統、状態は色＋文言 | トークン、badge |

注意・リスク

- 取り込みは「考え方」のみ。製品固有の用語・画面・挙動を再現済みとは書かない。
- 上表の出典の説明は一般知識で、公式未検索（未確認）。必要時は着手前に一次情報で確認する。ただしデジタル庁デザインシステムは 2026-10-21 に一次情報で確認済み（§12）。

## 4. データ設計規約

1. 全文書にスキーマ版 `v` を持たせる。版を上げる変更はユーザーの明示指示があるときだけ。
2. 入力の正規化を単一箇所（NORM）に集約し、保存・起動・スナップショット・復元の全経路で同一関数を通す。
3. 時刻は `YYYY-MM-DDTHH:mm+09:00`（JST・オフセット付き）。
4. id はホワイトリスト文字のみ。外部入力をそのまま id ・キーに使わない。
5. エラーは `{scope, ref, msg}` の構造で保持し、文字列だけで捨てない。
6. 読込に失敗した文書は、空データで上書きしない（readFail で保存を拒否）。
7. 監査文書は100件上限で古い順に落とす。
8. localStorage はユーザー単位の便宜（フィルタ・下書き）に限り、読み書きをすべて try/catch で囲む。正本を置かない。
9. バックアップのエクスポート/復元も NORM を通し、不正な型を取り込まない。

### スキーマ・文書構成の移行（5手順）

1. 旧データをエクスポートしてファイルに保存する（バックアップ）。
2. 新構造のデータを別ファイルとして生成する（旧データを直接編集しない）。
3. pinned（if\_version 指定）の batch で一括書込する。
4. 書込後に読み戻し、件数・主要項目を元データと突合する。
5. 旧文書の削除はユーザーが明示したときだけ。明示がない間は旧文書を残し、残存を報告する。

リスク

- batch は50件超で分割が必要。分割した場合、全体としては原子的ではない。途中失敗時はバックアップから復元する。

## 5. 画面・操作規約

1. デザイントークンは CSS 変数（`:root`）。ダークモードを `@media (prefers-color-scheme: dark)`（`:root:not([data-theme="light"])`）と `:root[data-theme="dark"]` の2系統で定義し、`body` に明示的な背景を持たせる。
2. iPhone 幅で完結する。左右16pxの余白、横スクロールなし、タップ領域44px以上。PC前提の操作（右クリック・ホバー必須）を使わない。
3. 状態表示は ok/warn/err/info の badge＋文言。色だけに意味を持たせない。
4. エラー文言は「何が・原因・次の行動」の3点。
5. 空・読込中・部分失敗の3状態をすべて表示する。
6. 確認ダイアログは不可逆操作（削除・復元上書き）のみ。
7. CSV は BOM 付き UTF-8。ファイル出力は downloads 機能を使う。
8. 標準動作（計算・提案・検索）はページ内で完結させる。AI は明示オプション（設定スイッチ）。
9. 操作対象（選択中の文書・表示状態）は、画面内で現在地が分かる形で表示する。

未確認

- 44px という値は一般的なタップ領域の目安で、本環境でこの値を実機検証していない。
- iPhone 実機の見え方は jsdom では再現できない。実機確認はユーザーに依頼する。

## 6. セキュリティ規約

基準: OWASP Top 10:2025（top10.owasp.org/2025 で項目名を取得済み）。LLM連携は OWASP LLM Top 10 2025（genai.owasp.org/llm-top-10 で取得済み）。以下の「本環境対策」は本環境の制約に合わせた実装規約であり、OWASPの記述そのものではない。

### 6.1 OWASP Top 10:2025 対応表

| 項目 | 本環境対策（規約） |
| --- | --- |
| A01 Broken Access Control | 公開範囲を公開結果で確認し、「リンクを知っている人」が読める状態を報告。共有設定は Claude が変更しない。DB・mcp は閲覧者権限で動くことを前提に設計。 |
| A02 Security Misconfiguration | capabilities を最小宣言（不要なものを宣言しない）。公開ごとに全量を再宣言し、差分を確認。contract を固定している場合は、新版との差を報告。 |
| A03 Software Supply Chain Failures | 外部 script は cdnjs / jsdelivr / unpkg 等の許可元のみ、版を完全固定。単一HTMLで完結する場合は外部依存ゼロを優先。 |
| A04 Cryptographic Failures | 機密（ID番号・カード・口座・パスワード）を DB・localStorage・バックアップに保存しない。バックアップファイルは平文。保管場所はユーザー責任として報告。 |
| A05 Injection | `innerHTML` への外部・ユーザー入力の直挿入を禁止。必須のエスケープ関数を通す。外部取得 HTML は DOMParser でホワイトリストのサニタイズ。`eval`/`new Function` はデータに適用しない。 |
| A06 Insecure Design | 不可逆操作にバックアップを必須化。外部取得失敗時は既存値保持（§2-9）。読込失敗時は上書き拒否（§4-6）。 |
| A07 Authentication Failures | 独自認証を実装しない（パスワード・トークンをページで扱わない）。認証はプラットフォーム側（claude.ai アカウント）に任せる。 |
| A08 Software or Data Integrity Failures | 読込・復元データを NORM で検証。バックアップは版 `v` と件数を確認。更新は if\_version で競合検出。 |
| A09 Security Logging and Alerting Failures | 変更とエラーを audit 文書に記録。重要エラーを運用チェックで表示。機密をログに残さない。 |
| A10 Mishandling of Exceptional Conditions | すべての非同期・外部呼出を try/catch。失敗を握り潰さず、{scope,ref,msg} で表示。部分失敗を明示。 |

※ A01、A04、A07 はプラットフォーム側で決まる部分が大きく、ページ側で完結できない。プラットフォームの内部挙動は未確認。

### 6.2 本環境固有の追加対策

1. 公開範囲: 公開結果の共有表示を毎回確認して報告する。個人データを扱うページは、共有をユーザーが変更するとデータ読取範囲が変わる可能性を明記する（mcp 共有時の権限は未確認）。
2. mcp は最小ツールのみ宣言（読取系のみ）。書込・送信・削除系ツールをページから呼べるようにしない。
3. 外部取得したコンテンツは信頼しない（データ扱い）。リンクは http/https のみ許可し、`javascript:` 等を除去。
4. LLM 連携（OWASP LLM Top 10 2025 のプロンプトインジェクション・出力の不適切な取扱・過度な権限付与に関連）: 入力はすべてデータ扱い。DB 内容も入力扱い。出力はスキーマ＋ref ホワイトリストで検証。LLM に書込権限を与えない。AI は明示選択時のみ。
5. ユーザー識別子（メールアドレス等）を無関係な外部サービスに送らない。
6. 過去版・バックアップに秘密を埋めない（公開履歴の保持仕様は未確認）。
7. テストハーネス（jsdom）は CSP を再現しない。CSP 由来の不具合は「実機未確認」として報告する。
8. iPhone 紛失・端末共有を想定し、画面に表示する個人情報（住所・予定・購入履歴）を最小化する。
9. 外部取得（TinyFish 等）のコスト・回数制限を無視しない。一括取得は件数上限を設ける（制限値は未確認）。

リスク

- 上記をすべて設定しても、ページ内のコード・データは閲覧者から見える。秘密を埋め込んではならない。
- A03 の具体的な許可元リストはプラットフォーム仕様で、変更されうる。公開時の拒否メッセージを優先する。

## 7. 品質・検証・報告

### 検証手順

1. タスクリストの最後を「検証」にする。
2. 変更前にページ・DBをバックアップする（ページは版ごとにファイル保存）。
3. 構文チェック: `new Function` で script をパース。
4. jsdom で全タブを巡回し、変更機能を個別に実行。外部呼出はモック。
5. DB 変更は読み戻して突合。
6. 公開結果（共有表示を含む）を確認。
7. チェックできなかった項目は「未確認」として報告。

### 報告形式（監査指摘形式・最小）

- 結論
- 修正点
- 未確認・不可
- 問題点・リスク（肯定のみの報告をしない）
- Sources（ツールで実際に取得した情報源のみ）

### 判定基準

- jsdom で通り、実機を確認していない機能は「実機未確認」とする。
- 定量的な主張（速度・件数）は計測値と計測環境（jsdom）を併記する。
- ユーザーの訂正を受けたときは、反映範囲を列挙して報告する。

## 8. 公開・変更管理・運用

1. 既存のページは同一ファイルパスで更新する。別パスは別アプリを作るときだけ。
2. 公開ラベルに「V番号＋要約」を付け、変更内容を追えるようにする。
3. 公開ごとに capabilities を全量で再宣言する（省略と空オブジェクトの挙動差に注意）。
4. 変更を分類する: (a) ページのみ変更／(b) データ変更／(c) スキーマ変更。(b)(c) は §4 の移行手順とバックアップを必須とする。
5. ロールバック用に前版のページファイルを残す。
6. 公開結果の共有表示が変わった場合、変更した設定はユーザーに報告する（Claude は共有を変更できない）。
7. ユーザーが編集した可能性のあるページは、更新前に現在の公開版を読み、競合を確認する。
8. 継続セッションでコンテキストが圧縮された場合は、ページファイルの最新コピー（スクラッチパッド）を正本として扱う。

リスク

- スクラッチパッドはセッション単位で、セッション終了後の保持は未確認。公開済みページからの read をバックアップ手段とする。

## 14. 業務要件→要件定義 変換ロジック（RT）

【着想】本書独自。EARS（要件記法）を文型に借用。検証結果は 14.9。業務部門が曖昧・自由記載で書いた要望を、システム要件文・受入基準・§9 依頼テンプレートへ機械的に変換する。

### 14.1 使い方（業務部門向け・3手順）

- 手順1: 困りごと・やりたいことを、そのまま書く。曖昧でよい。IT用語は不要。例「月末の請求書チェックが大変。間違いがないようにしたい」
- 手順2: AI が質問を出す。選択肢で答える。1回5問まで。「分からない」も有効な回答。
- 手順3: AI が「読み戻し文」を出す。違う箇所だけ直す。OK と答えた内容が依頼書（§9）になる。
- AI は目的・範囲・数値・承認者などを決めない。聞く（14.3）。

### 14.2 変換規則 RT-1〜RT-9

- RT-1 原子化: 入力を句点・読点で 1文＝1要求に分け、S1, S2… の ID を付ける。原文は改変せず保持する。前後6字未満の断片は隣と結合する。
- RT-2 スロット検出: 各要求について 誰が／何を／いつ・きっかけ／どうする／どれくらい／例外 の有無を見る。欠落は推測で埋めず、質問にする。
- RT-3 曖昧語照合: 14.4 の辞書で照合する。1語でも該当すれば、その要求は「要確認」。該当語ごとに対応する質問を必ず出す。
- RT-4 タイプ分類: 14.5 の10タイプのいずれかを付ける（複数可）。該当なしは「分類不能」とし、Q-PURPOSE を出す。
- RT-5 機能候補の写像: 14.6 の語一致で F1〜F7 等を「候補」として付す。候補は採用ではない。採否は §13 の基準で判定し、決定はユーザー（13.7）。
- RT-6 質問規則: 14.7 の固定順で出す。1ラウンド5問まで。選択式を原則とする。同じ質問を繰り返さない。必須質問（G-NEWEXIST, G-DATA, G-ENV, G-ENVCHK, G-USERS, G-DONE, G-PURPOSE の7問は依頼ごとに1回、G-PRIORITY は要件ごとに1回）は必ず出す。
- RT-7 要件文化: 回答が揃った要求だけを 14.8 の文型で要件文にする。未回答の項目は【未確定】と明記して残す。推測で埋めない。
- RT-8 確定条件: 「確定候補」は、曖昧語なし かつ スロット欠落なし かつ タイプ分類可、の全てを満たす要求だけ。それ以外は「要確認」。「確定」はユーザーの読み戻し承認でのみ成立する。
- RT-9 出力: 要件一覧（ID・原文・タイプ・要件文・受入基準・機能候補・状態）と、§9 依頼テンプレートの自動記入結果、§13 判定（機能候補ごと）を出す。最後に平易な読み戻し文を出す。

### 14.3 AI が決めてよいこと／ユーザーに聞くこと

- AI が決めてよい: 表現の整形、ID 付番、タイプ分類、辞書照合、機能候補の提示、14.10 の安全側既定値の適用（適用したと明記する）。
- ユーザーに聞く: 目的、対象データ、個人情報・機密の有無、「など・その他」の中身、数値（件数・日数・期限・閾値）、判断者・承認者、閲覧範囲、優先度、完了条件、使う環境。
- ユーザーの回答と矛盾する既定値は適用しない。

### 14.4 曖昧語辞書（A〜H。検証版 84語）

- A 程度・主観 → Q-NOW, Q-VOL, Q-FREQ: すぐ／早く／なるべく／できるだけ／簡単／分かりやすい／わかりやすい／見やすい／いい感じ／ちゃんと／ちゃんとした／しっかり／適切／適宜／必要に応じて／大変／面倒／楽に／スムーズ／使いやすい
- B 量 → Q-VOL: たくさん／多い／少ない／少なく／少し／大量／いくつか／大体／多数
- C 範囲 → Q-LIST: など／その他／全部／すべて／全て／いろいろ／色々／各種／一式／諸々
- D 時 → Q-FREQ, Q-DEADLINE, Q-WHEN: 定期的／随時／都度／月末／期限まで／そのうち／最近／早め／遅れ／たまに／毎回／近い／滞
- E 人 → Q-WHO, Q-DECIDE: 担当者／関係者／上長／上司／みんな／誰でも／先方
- F 結果の保証 → Q-ERR, Q-CHECK: 間違／ミス／漏れ／抜け／忘れ／二重／ダブり／滞らない／チェック
- G 指示語・省略 → Q-REF: それ／あれ／例の／いつもの／前と同じ／同様／同じ形式／前と同
- H 例外・条件 → Q-EX: 基本的／原則／ただし／場合によ／例外／特別／除く／以外
- 規則: 語が別の語に包含される場合（例「ちゃんと」と「ちゃんとした」）は長い語のみ数える。辞書にない曖昧語は検出できない（14.9 の限界）。辞書の追加・変更は版数付きの改訂提案で行い、同一基準を保つ（13.1）。

### 14.5 要件タイプ

- BF 業務フロー（申請・承認・差戻し・進捗・状態）／DT データ（台帳・マスタ・項目・履歴）／UI 画面・入力・検索／CL 計算・判定・照合／NT 通知・期限／AC 権限・閲覧／IF 取込・出力・連携／NF 非機能（件数・端末・保存期間）／CN 制約・規程（個人情報・社外持出し）／OP 運用（保守・引継ぎ）
- 非機能（NF）の質問項目は IPA「非機能要求グレード」の大項目（可用性・性能拡張性・運用保守性・移行性・セキュリティ・システム環境）を参照する。取込範囲は Q-ENV, Q-KEEP, Q-VOL, Q-VIEW に限る。

### 14.6 機能候補の写像（候補であり採用ではない）

- F1 入力規則: 間違／ミス／必須／形式／桁／範囲／入力
- F2 変更履歴と復元: 履歴／誰がいつ／変更／元に戻／記録を残／監査
- F3 状態遷移と承認: 申請／承認／差戻／却下／ステータス／状態／進捗／確認済／完了／滞

- 既存規約: 重複／二重／ダブり → §3 重複検出。取込／出力／CSV／Excel／貼り付け → §5 の CSV 取込・出力規約。
- 語一致は偽陽性を含む（例「形式」で F1 が付く）。付いた候補は質問 Q-OUT／Q-ERR の回答で絞る。

### 14.7 質問バンク（固定順。22問）

- Q-PURPOSE 誰の、どんな作業を、どうなったら助かりますか？（例付き自由記載）［必須］
- Q-WHO この作業をするのは誰（役割）で、何人くらいですか？（1人／2〜5人／6〜20人／21人以上）
- Q-NOW 今はどうやっていますか？（Excel／紙／メール／既存システム／その他）
- Q-ERR どんな間違い・困りごとが起きていますか？（入力ミス／転記ミス／抜け・漏れ／二重／期限超過／その他）
- Q-CHECK 「チェック・確認」は何と何を突き合わせることですか？（照合元と照合先）
- Q-WHEN いつ、何がきっかけで始まりますか？（毎日／毎週／毎月（何日）／発生したとき／その他）
- Q-FREQ どのくらいの頻度ですか？（毎日／週1／月1／不定期）
- Q-VOL 1回に扱う件数は？（〜10件／〜100件／〜1,000件／それ以上）
- Q-DEADLINE 期限は？何日以内、何日前に気づきたいですか？（当日／3日／7日／その他）
- Q-DECIDE 誰が判断・承認しますか？（役割で）
- Q-LIST 「など・その他・全部」に含まれるものを全て挙げてください。
- Q-REF 「それ・前と同じ・いつもの」は具体的に何ですか？（見本添付可）
- Q-EX 例外はどんな場合で、どう扱いますか？
- Q-NOTIFY 気づけないと困ることは？誰にいつ知らせますか？（画面内表示で足りるかも確認）
- Q-WHAT-DATA 扱う情報に個人情報・機密は含まれますか？（含まない／個人情報／機密／両方）［必須］
- Q-VIEW 誰にどの情報まで見せてよいですか？（全員／部署内／本人と上長のみ／その他）
- Q-OUT 結果はどう使いますか？（画面で見る／CSV で出す／印刷／他システムへ渡す）
- Q-KEEP 記録をどれくらい残しますか？（1か月／1年／3年／ずっと／分からない）
- Q-ENV どこで使いますか？（PC／スマホ／社内のみ／社外からも）［必須］
- Q-END 何ができたら「終わり」ですか？
- Q-DONE できたか、どう確かめますか？（確かめ方の例を1つ）［必須］
- Q-PRIORITY それぞれ「絶対必要／あれば良い／今回はいらない」のどれですか？［必須］
- 欠落スロットとの対応: 誰が→Q-WHO、何を・どうする→Q-PURPOSE、いつ・きっかけ→Q-WHEN、どれくらい→Q-VOL。

### 14.8 要件文の文型（EARS 5パターン＋複合）

- 常時: 「システムは、<応答>しなければならない。」
- 事象: 「<きっかけ>のとき、システムは、<応答>しなければならない。」
- 状態: 「<状態>の間、システムは、<応答>しなければならない。」
- 望ましくない状況: 「<望ましくない状況>の場合、システムは、<応答>しなければならない。」
- 任意機能: 「<機能>を備える場合、システムは、<応答>しなければならない。」
- 複合: 上記を組み合わせる。
- 受入基準は「<操作>すると<結果>になる」の1文で書く。数値は回答値のみを使う。回答がない数値は【未確定】とする。
- 例（回答済みの場合のみ）: 「経理担当が請求書を登録するとき、システムは、金額が数字以外なら登録を拒否し、理由を表示しなければならない。」← F1 候補。

## 15. 共有データの排他制御・時刻・参照通信（v5 で追加）

複数人または複数セッションが同じデータを更新する業務ツールに適用する。単独利用のツールには適用しない。14.13 の変換ツールは対象外で、通信なしのままとする（リリース前ゲート⑥は変更しない）。区分の表記は §0 に従い、本章では【確認済】（取得した情報源あり）、【実測】（参照実装の試験結果。実行は作業環境の Node で、社用環境ではない）、【評価】、【未確認】を使う。

### 15.1 基本原則

1. ロックに依存しない。正しさは、ロックの有無・取得順・到着の遅れ・重複に左右されない。
2. 書込みは追記のみとし、書込み主体ごとに専用のファイルを持つ。他者のファイルを更新・削除しない。
3. 競合は検出して表示し、黙って捨てない。解決は利用者が行い、履歴に残す。
4. 並行の判定に時刻を使わない。因果関係（親イベント）だけで判定する。時刻は表示と暫定表示の順序にだけ使う。
5. 性能のための最適化（キャッシュ・差分読込）は、正しさに影響させない。最適化を外しても同じ結果になること。
6. 外部への通信は参照のみ・データのみ・許可リスト内に限る。失敗しても業務操作は止めず、同梱の既定値で縮退する。
7. 検証していない保証を書かない。実機で測っていない項目は【未確認】とし、15.11 の測定を終えるまで運用の前提にしない。

### 15.2 方式の比較（【評価】）

| 方式 | 排他の強さ | 判定 | 理由 |
| --- | --- | --- | --- |
| 共有 JSON 上のロック（従来） | 協調的。取得と書込みの間に隙がある | 不採用 | ロック残り・同期遅延・同時取得で破綻する。誤ったときに上書きが起きる |
| 共有 JSON への楽観的排他（ETag と If-Match。不一致は 412） | 強い（保存先が原子的に判定） | 条件付き | 保存先の API をページから呼べる場合のみ。呼べるかは【未確認】。ETag・If-Match・412 は SharePoint REST と Graph の仕様として確認済（[SharePoint ETag の解説](https://sympmarc.com/?p=24702)、[Graph driveItem 更新](https://learn.microsoft.com/en-us/graph/api/driveitem-update)） |
| ファイルのチェックアウト | 強い | 不採用 | API 経由の操作可否が【未確認】。残留チェックアウトの解除手順が必要 |
| 追記専用イベント＋読込時マージ（本章） | 衝突しない設計。競合は検出して表示 | 採用 | ロック不要。保存先に API がなく、ファイルの作成と読取りだけでも成立する |
| ブラウザ内の排他（Web Locks、BroadcastChannel、IndexedDB） | 同一ブラウザ内のみ | 補助のみ | Web Locks はオリジン単位で、ブラウザやプロファイルをまたぐ挙動の記載がない（[MDN](https://developer.mozilla.org/docs/Web/API/Web_Locks_API)、確認済）。他の利用者には効かない |
| File System Access の exclusive 書込み | 同一端末のブラウザ内のみ | 補助のみ | ライターを1つに制限するが、書込みは close 時に元ファイルを置換し、標準の siloed では最後に close した内容が残る（[MDN](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/createWritable)、確認済）。同期経由の他者の編集は防げない |

### 15.3 データ構造

ファイル配置（保存先のフォルダ。同期フォルダまたは API のいずれでも同じ構造）:

- `events/s_<w>_<k>.jsonl`: 書込み主体 `w` の `k` 番目のセグメントを1行1イベントで保持する。書くのは `w` 本人だけ。
- 書込み主体 `w` はページを開いたときに毎回新しく作るランダム値（128ビット、16進数字）。端末・利用者・タブごとに異なる。枠の割当てやリースは使わない。RDP での複数セッション・複数タブでも調整が不要になる。

イベント（1行の JSON。キーをソートした正規化形式で書く）:

| 項目 | 内容 |
| --- | --- |
| `v` | 1 固定。未知の版を含むデータは読取専用にする |
| `id` | `<w>:<n>`。`n` は書込み主体内の連番（0始まり・欠番を許さない） |
| `rid` | 対象レコード。`[A-Za-z0-9_-]{1,64}`（ホワイトリスト。`__proto__`・`constructor`・`prototype` は拒否） |
| `op` | `set`（変更）、`res`（競合の解決。親はその時点の全 heads） |
| `f` | 変更するフィールドと値。フィールド名は `[A-Za-z_][A-Za-z0-9_]{0,63}`。削除は `_del:true`、復元は `_del:false`（論理削除） |
| `parents` | 編集時点で本人が見ていた当該レコードの先頭イベント（heads）の id |
| `hlc` | `[ms, counter]`。混合論理時計（§15.6） |
| `ts` | JST 表記（`2026-10-22T01:11:05.123+09:00`）。表示用 |
| `tsrc` | `ext`（参照通信で補正済）、`fs`（保存先の時刻）、`local`（端末時計）、`local-suspect`（端末時計で、ずれの疑いあり） |
| `by` | 利用者名（自己申告。§15.7） |
| `prev` | 同じ書込み主体の直前イベントの `h`（先頭は null） |
| `h` | `h` 以外を正規化した JSON の SHA-256 |
| `dr`（任意） | 推定した端末時計のずれ（ms）。`tsms` は書き換えず、補正値を別記録する |

- 1イベントは正規化後 16,384 文字以内。超える場合は拒否して分割を促す。
- SHA-256 は埋込みの純 JS 実装を標準とする。Web Crypto が社用の実行方式で使えるかは【未確認】。
- スキーマを変更するときは §4 の手順に従い、`v` を上げる。旧版のイベントは読めるようにして残す。

### 15.4 書込み手順

1. 入力を確定したら、イベントの元になる「意図」（`rid`、`f`、編集時点の `parents`、時刻）を端末内の IndexedDB（送信待ち）に保存する。保存できない場合はメモリ上で続行し、「送信待ちが端末に残らない」を表示する。
2. 意図からイベントを生成する（`id`、`hlc`、`prev`、`h` を付与）。`parents` は編集時点の値を保持する（送信が遅れても「何を見て編集したか」が変わらない）。
3. 自分のアクティブなセグメント `s_<w>_<k>.jsonl` を、全体を書き直す形で保存する（完了時に元ファイルを置換する保存方式を使う。File System Access の createWritable は close 時に置換：確認済）。新規ファイルの作成は「作成専用（既に存在すれば失敗）」で行う。API 経由の指定方法は【未確認】。
4. 書込み後に読み戻し、自分の全イベントの `id` と `h` が一致したときだけ送信待ちから削除する。
5. 失敗したときは送信待ちを残し、上限付きの指数間隔で再試行する。再送しても同じ `id` と同じ `h` なので重複しない。画面に未送信件数を常時表示する。
6. セグメントは 200 イベントまたは 256 KB を超えたら次の番号 `k+1` に切り替え、以後前のセグメントは更新しない（書き直しの量を押さえるため。数値は暫定で実測未実施）。
7. 他者のファイルを書き換え・削除しない。実装上も、書込み関数は自分の書込み主体のファイル名以外を受け付けない。
8. ページを再読込したときは新しい書込み主体で始める。送信待ちの意図は新しい `w`・`n` で再発行する。
9. 保存先への書込み権限がない、または File System Access の権限が得られない場合は読取専用で開く。セッション開始時の権限再確認の有無と挿動は【未確認】（§15.11 M6）。

### 15.5 読込みとマージ規則

マージは「イベントの集合 → 状態」の純粋関数とする。到着順・ファイル順・重複に依存しない（§15.11 G1）。

1. 列挙: `events/` 配下の全ファイルを列挙する。前回から名前・サイズ・内容が変わらないファイルは再読込しない（最適化。§15.1 原則 5）。
2. 検証: 各行を JSON として読み、形式と `h` を検証する。ファイル末尾の途中で切れた行は無視して次回再読込する。途中の不正行はその行だけ隔離し、画面に警告を出して他は継続する。
3. 重複: 同じ `id` と同じ `h` は1件として扱う。同じ `id` で `h` が異なるものは完全性違反として警告し、`h` の小さい方を採用する（決定的に選ぶ）。
4. 因果配送: `parents` が全て同じ `rid` で揃うまで、そのイベントを「同期待ち」として保留する（状態に反映しない）。親が別の `rid` を指すイベントは永久に保留して警告する。
5. フィールドの候補: あるレコードのあるフィールドを設定したイベントのうち、「同じフィールドを設定した他のイベントの祖先ではないもの」を候補とする（支配されていない設定）。候補の値が1種類ならその値、同じ値を並行して設定した場合も競合にしない。
6. 競合: 候補の値が2種類以上あるときは競合とする。競合したフィールドは「競合あり」として一覧に出す。
7. 暫定表示: 競合中の値は、候補のうち `hlc` が最大のもの（同値なら `w`、`n` の順）を「暫定」として示す。候補に `local-suspect` 、または信頼できる現在時刻より許容誤差を超えて未来の `hlc` が含まれるときは、暫定値を示さず「未確定」とする（自動採用しない）。
8. 解決: 利用者が選んだ値で `op:res` を発行する。`parents` はその時点の当該レコードの全 heads。履歴からの再採用も同じ。解決後に再び並行の変更が入った場合だけ競合に戻る。
9. 削除・復元もフィールド `_del` として同じ規則でマージする（削除と編集の並行も競合として見える）。
10. 状態はフィールド単位で選ぶ。レコード全体をどちらかの版で上書きすることはしない。違うフィールドへの並行編集は競合しない。

【実測】参照実装で上記 4〖10 を検証した（§15.11）。参照実装はリポジトリの `docs/reference/exclusive-control/` にある。

### 15.6 時刻の規約

HTML 単体では真の現在時刻を知る手段がない。端末時計の誤差を補正するには外部の時刻源が要る。ただし本規約では、並行の判定を時刻に依存させない（§15.1 原則 4）。時刻の誤差は、暫定表示の順序と表示と監査上の信頼度にだけ影響する。

1. 表記は JST 固定。`ts` はオフセット `+09:00` 付きで、`Intl.DateTimeFormat` に `timeZone:"Asia/Tokyo"` を指定するか、`tsms+9時間` を計算して生成する。端末のタイムゾーン設定（RDP のタイムゾーンリダイレクトを含む）に左右されない。画面表示も同じ関数を使う。
2. 混合論理時計（HLC）: `hlc=[ms,counter]`。発行時は `ms=max(現在時刻, 直前の hlc.ms)`、同じ `ms` なら counter を +1。他者のイベントを読んだときも、大きい方を取り込む。これにより、後ろにずれた端末でも、自分が読んだイベントより小さい `hlc` を発行しない。
3. 未来側の汚染防止: 信頼できる現在時刻（下記 4 の参照通信で得た値）があるとき、それに許容誤差を足した値より大きい `hlc` は取り込まない。取り込むと、進んだ時計の端末が全員の `hlc` を引き上げてしまう。
4. 時刻源の優先順: ① 参照通信の時刻（§15.9。`tsrc:ext`）② 保存先が付ける更新時刻（`tsrc:fs`。同期クライアントがローカル時計を保持する場合は補正にならない。【未確認】）③ 端末時計（`tsrc:local`）。記録時に採用した時刻源を `tsrc` に残す。
5. 参照通信の時刻は、複数の時刻源を使い、差が 60 秒以内のときだけ採用する。採用後は `オフセット=外部時刻−端末時計` を保持し、`now=端末時計+オフセット` として使う。取得は起動時と、以後 30 分ごと。`tsms` は補正後の値を記録し、補正量を `dr` に残す。
6. 端末時計のずれ検知（参照通信が使えないとき）: 起動時に `現在時刻` を全イベントの最大 `hlc.ms` と比べ、許容誤差 `CLOCK_TOLERANCE_MS` を超えて遅れていれば、「この端末の時計が遅れている可能性」を常時警告し、以後のイベントに `tsrc:local-suspect` を付ける。進んでいる方向はこの方法では検知できない（参照通信が必要）。
7. `CLOCK_TOLERANCE_MS` = 300000（5分）。HTML 冒頭の定数とし、変更した値は起動時の設定記録（§15.7）に残る。根拠は、Windows ドメインの Kerberos が既定で 5 分を超える時計じれを拒否するという理解であり、今回は検索していないため【未確認】。社用の実測値が得られたら差し替える。
8. 参照通信が使えない場合は端末時計で続行する（書込みを止めない）。上記 6 の警告と `tsrc` で信頼度を区別する。監査上、`tsrc:ext` を必須にしたい業務は定数 `REQUIRE_EXT_TIME=true` で、取得できない間は書込みを止める（既定は false）。
9. 端末時計が「進んでいる」ことを検知できない間は、並行編集の暫定表示が誤って進んだ端末の値になることがある。競合は常に表示され、両方の値が履歴に残るため、値は失われない。

### 15.7 完全性・監査

1. ハッシュ鎖: 各イベントは自身の `h` と、同じ書込み主体の直前イベントの `h`（`prev`）を持つ。改ざん、途中の欠落、連番の欠番を検出する。検出したときは該当件数を画面に表示し、該当行を状態に反映しない。
2. 追記専用: 既存行の変更・削除をしない。訂正も削除も新しいイベントとして追記する。イベント自体が監査証跡となる（誰が、いつ、何を見て、何を変えたか）。
3. 利用者の同一性: `by` は自己申告であり、ページ側では認証できない。監査上の証明力が必要な場合は、保存先が記録するファイルの作成者・更新者のメタデータと `by` を照合し、不一致を警告する。メタデータをページから取得できるかは【未確認】（§15.11 M7）。取得できない間は、`by` は証拠ではなく参考情報として扱う。
4. 入力の検証: フィールド名・`rid`・`id` はホワイトリスト文字のみ。サイズ上限を超える行、未知の種別の `op`、`tsrc` を拒否する。表示時は値をテキストとして扱い（`textContent`）、`innerHTML` に渡さない。
5. 隔離リスト: 拒否した行のファイル名・行番号・理由を画面で確認できるようにし、削除・修復はしない。修復は管理者が別途判断する。
6. 監査ログ: 設定定数（`CLOCK_TOLERANCE_MS`、`REQUIRE_EXT_TIME`、参照通信の許可リストの版）を起動時にイベントとして記録する。定数を変えたページの版で書くイベントは、どの版の設定で書かれたかを追える。

### 15.8 性能・保持・削除

【実測】参照実装（Node、作業環境。社用端末のブラウザではない）のマージ時間とメモリ:

| レコード数 × 1レコードのイベント数 | 全イベント数 | 時間 | メモリ（プロセス全体） |
| --- | --- | --- | --- |
| 200 × 100 | 20,000 | 0.53 秒 | 133 MB |
| 20 × 1,000 | 20,000 | 4.2 秒 | 378 MB |
| 1 × 2,000 | 2,000 | 0.93 秒 | 434 MB |
| 1 × 5,000 | 5,000 | 8.5 秒 | 827 MB |

コストは「全体の件数」ではなく「1レコードあたりの履歴の長さ」で増える（祖先集合を保持するため、2乗で増える）。端末の性能はこの表より悪い可能性がある。

1. 運用上限（暫定）: 1レコードあたり 200 イベントを超えたら、画面に警告を出す。超えたレコードの有無を監査ログに残す。上限値は社用端末での実測（§15.11 M8）で確定する。
2. 読込キャッシュ: 検証済みのイベントを IndexedDB に保存し、前回から変わっていないファイルを再読込しない。キャッシュを捨てても同じ状態になること（§15.1 原則 5）。
3. 履歴は削除しない。削除と復元は `_del` の追記。個人情報の物理削除を求められる業務では、本方式は適用できない（別方式を選定する）。
4. ファイルの統合・退避・基準更新（compaction）は本版では規定しない。候補を決める「祖先関係」を保ったまま縮退する設計と、古い端末から遅れて届くイベントの扱いが未検証であるため。将来規定する場合の要件: ① 決定的で、誰が作っても同じ内容になる ② 作成専用で、既存ファイルを更新・削除しない ③ 縮退前後で同じ状態・同じ競合を返す ④ §15.11 の G1〜G6 を同じ基準で通す。

### 15.9 参照通信（§1 の「外部通信なし」の例外規定）

既定は通信なし（§1、14.10）。本節の例外は、着手時に「参照通信: あり」と宿言したツールにだけ適用する。許可するのは「データの参照（取得）」だけで、こちらから業務データを送ることは許可しない。

【確認済】参照の設計に関わる事実:

- クロスオリジンの fetch でページから読める応答ヘッダーの標準の一覧に `Date` は含まれない。サーバーが `Access-Control-Expose-Headers: Date` を返したときだけ読める（[MDN](https://developer.mozilla.org/en-US/docs/Glossary/CORS-safelisted_response_header)）。時刻の参照は、応答の本文（JSON）に時刻を含むサービスを優先する。
- 公開の時刻 API の一例（worldtimeapi.org）は、SLA なし・長期停止あり・商用利用非推奨・過度のアクセスは制限、と明記している（[FAQ](https://worldtimeapi.org/pages/faqs)）。社用の標準時刻源にしない。
- 「日本標準時の供給サービスで異常、誤った時刻を配信」という見出しの記事が 2026-10-02 にある（[ScanNetSecurity](https://scan.netsecurity.ne.jp/article/2026/10/02/56369.html)）。本文は取得できなかったため、対象・原因・期間は【未確認】。単一の時刻源に依存しない設計の根拠の一つとする。

#### 15.9.1 許可リスト（登録簿）

通信先は HTML 内の登録簿に固定し、利用者入力から URL を組み立てない。登録する項目:

| 項目 | 内容 |
| --- | --- |
| `id` | 分類名（`time` / `master` / `rules` / `public`）＋連番 |
| `url` | 固定の HTTPS URL（1件ずつ。パターン指定は不可） |
| 形式・スキーマ | JSON または CSV。許可するキーと型・範囲 |
| 最大バイト・タイムアウト | 超えたら破棄 |
| 保持期間（TTL） | キャッシュの有効期間 |
| 固定ハッシュ | `rules` は必須（判定ロジックに影響するデータ）。SHA-256 を照合し、承認済みの版だけ採用する |
| 縮退値 | 取得できないときに使う同梱の既定値 |
| 目的・データ区分 | なぜ必要か。個人情報を含むか |
| 有効フラグ | 個別に無効化できる（全体スイッチ `EXT_ENABLED` も持つ） |

#### 15.9.2 要求の規則

1. メソッドは GET のみ。クエリ文字列・ヘッダー・URL パスに、業務データ・個人情報・利用者 ID を載せない。
2. 公共データへの fetch は `credentials:"omit"`、`referrerPolicy:"no-referrer"`、`redirect:"error"`、`cache:"no-store"`（時刻）を指定し、`AbortController` でタイムアウトさせる。
3. 社内データ（SharePoint や Graph）への認証は、実行環境が提供する方式だけを使う。トークン・資格情報を HTML に埋め込まない。認証方式と呼べるか自体が【未確認】（§15.11 M4）。
4. 取得するのはデータ（JSON・CSV・テキスト）だけ。スクリプト、CSS、フォント、iframe、画像の外部取得は行わない（取得物が実行コードになる、または追跡に使えるため）。ライブラリは HTML に同梱する（§1）。

#### 15.9.3 応答の取り扱い

1. Content-Type、サイズ上限、JSON としての構文、スキーマ（許可したキーと型・範囲）を検証する。未知のキーは捨てる。一つでも不適合なら応答全体を破棄する。
2. 文字列は `textContent` で表示する。`eval`、`new Function`、`innerHTML` に渡さない。
3. 判定ロジックに影響するデータ（`rules`）は、SHA-256 が登録簿の値と一致したときだけ採用する。更新は登録簿のハッシュを変えたページの新版として公開する（承認を経る）。
4. 縮退順: ① 取得成功 → ② TTL 内のキャッシュ → ③ 期限切れキャッシュ（「古いデータ」と表示） → ④ 同梱の既定値。いずれでも業務操作は止めない（`REQUIRE_EXT_TIME=true` の書込みを除く）。
5. CSP やプロキシで遮断された場合も同じ縮退に入り、「参照通信: 遮断」を状態表示に出す。失敗の理由を区別できない場合は「失敗」として扱う。
6. 監査ログに、通信先の `id`、時刻、結果（成功/失敗/遂断/ハッシュ不一致）、バイト数を記録する。応答の中身は記録しない。

#### 15.9.4 時刻の参照

- 複数（2、3件）の時刻源を登録し、差が 60 秒以内のときだけ中央値を採用する。外れたときは破棄して端末時計で続行する（§15.6）。
- 社内の時刻源が使える場合は、公開の無保証 API より優先する。使えるかは【未確認】。

#### 15.9.5 参照先の候補（【評価】。すべて到達性・CORS・提供条件が【未確認】）

| 分類 | 例 | 増える機能 | 注意 |
| --- | --- | --- | --- |
| `master` | SharePoint/Graph の読取り（マスタ・組織・設定） | マスタ照合、入力補完 | 認証方式が未確認。閲覧権限に限る |
| `rules` | 更新配信 JSON（辞書・ルール・版情報） | HTML を再配布せずに辞書を更新 | 判定が変わるため、ハッシュ固定と承認済み版のみ |
| `public` | 祝日 CSV（内閣府） | 営業日計算、期限日の自動算出 | 文字コードと形式。提供元の仕様変更 |
| `public` | 郵便番号・住所 | 住所補完 | 入力した郵便番号が URL に載る。個人情報を含む場合は不可（全件取得して端末内で絞る方式にする） |
| `public` | 為替・法令（e-Gov） | 換算、条文の参照 | 提供元の安定性・利用条件 |
| `time` | 時刻の API（2〜3件） | 時刻の補正 | §15.9.4 |

§14.13 の変換ツールは本節の対象外であり、引き続き通信を行わない。

### 15.10 画面要件

§5 の画面・操作規約に加えて、次を満たす。すべて iPhone 幅で崩れないこと。

1. 状態表示（常時。画面上部の1行）: 最終読込時刻（JST）、未送信 N 件、同期待ち N 件、競合 N 件、隔離 N 件、時刻の状態（補正済み / 端末時計 / ズレ疑い）、参照通信の状態（成功 / キャッシュ / 遮断 / 無効）。赤・黄の色だけで区別せず、文言を併記する（§12 の色規約）。
2. 競合一覧: フィールドごとに候補の値、書いた人（`by`）、JST 時刻、時刻源（`tsrc`）、「暫定」または「未確定」を示す。候補をタップして 1 操作で `op:res` を発行する。確認ダイアログは省略しない（選んだ値を表示してから確定）。
3. `local-suspect` を含む候補には警告を付け、自動採用しない。
4. レコード詳細に履歴を表示する（誰が、いつ、何を見て、何を変えたか）。履歴からの再採用は `op:res` として追記する。
5. 未知のイベント版を見つけたときは読取専用にし、理由を表示する。書込権限がない場合も同じ。
6. 「他者の変更は同期の遅れで反映が遅れることがあり、競合は後から表示される」を利用者向けの説明（1行）として表示する。

### 15.12 注意・リスク

- 端末時計が「進んでいる」ことは、参照通信の時刻が無いとき検知できない。並行編集の暫定表示が誤って進んだ端末の値になりうる。競合は常に表示され、両方の値が履歴に残るため、値は失われない。
- `by` は自己申告。保存先のメタデータと照合できるかは【未確認】（M7）。監査上の本人確認には単独では使えない。
- 履歴は消えない。個人情報の物理削除を求められる業務には適用できない。
- 読込コストは 1 レコードあたりの履歴の長さで増える（実測: 1,000 イベントで 4.2 秒、378 MB）。compaction は未規定のため、運用上限を超えたレコードは新しいレコードに分ける運用で回避する。
- 同期遅延の間は他者の変更が見えない（結果整合性）。競合は後から表示される。即時の排他（「今このレコードを他の人が開いている」の表示）はこの方式では保証しない。必要な場合は「編集中」の表示を参考情報として追記する（ロックではない）。
- ファイル同期の競合コピー（同一ファイルを複数端末で同時更新したときに生じる）は、書込み主体ごとに専用ファイルにすることで発生を避ける設計だが、発生しないことは未実測。競合コピーのファイル名を見つけたときは、読み込まずに隔離リストへ出す。
- 参照通信先の改ざん・停止・仕様変更。ハッシュ固定（`rules`）と縮退値で影響を押さえるが、時刻と公共データはハッシュ固定できない（時刻は複数源の照合で代替）。
- 参照通信のリクエスト自体が、利用者の IP や利用時刻を相手先に見せる。許可リストの候補を選ぶときに何を見せてよいかは情報システム部門と確認する（社内の規定は【未確認】）。
- この章の内容は参照実装（Node）での検証と、公開情報の確認に基づく。社用環境での動作は、§15.11.3 の測定を終えるまで保証しない。

| セッション枠（slot）＋リース（30 秒更新・90 秒失効） | 起動ごとの書込み主体 ID。リースは使わない | リースは同期遅延と同時起動に強く依存する協調方式で、§15.1 原則 1（ロックに依存しない）に反する |
| 並行判定に `base`（見ていた最新イベント ID 1つ） | `parents`（見ていた全 heads） | heads が複数あるときに 1 つでは並行を表せない。フィールド単位の支配関係が定義できる |
| 暫定採用は `tsms` の大小 | HLC（`hlc`）＋未来じれの「未確定」 | 後ろにずれた端末が読んだイベントより前の時刻を付けない。進んだ時計の汚染を押さえる |
| ID は UUID | `<w>:<n>`（書込み主体＋連番） | 重複除去が自明で、欠番から欠落を検出できる |
| セグメントの封とスナップショット | 規定しない（§15.8） | 候補の祖先関係を保った縮退は未検証。無理に規定しない |
